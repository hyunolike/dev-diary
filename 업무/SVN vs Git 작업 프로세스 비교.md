## SVN vs Git 작업 프로세스 비교 (작업 과정, 브랜치 전략)
> 작성날짜: 25.02.23

### 요약
- SVN은 모든 커밋이 직접 중앙 저장소에 반영

<img width="543" alt="image" src="https://github.com/user-attachments/assets/329d22b2-ccb1-4bb8-8de8-4db76ef27587" />

### 주요 차이점
#### 1. 저장소 구조
##### SVN: 중앙 저장소만 존재
```
모든 커밋이 직접 중앙 저장소에 반영됨
오프라인 작업이 제한적
```

##### Git: 로컬 저장소 + 원격 저장소
```
로컬에서 커밋 후, 원격에 푸시하는 2단계 과정
오프라인 작업 가능
```

#### 2. 작업 과정 SVN의 기본 작업 과정
- `update`: 중앙 저장소의 최신 변경사항을 받아옴 (Git의 pull과 유사)
- `commit`: 변경사항을 바로 중앙 저장소에 반영 (Git의 commit + push와 유사)

### Git의 작업 과정
- add: 변경사항을 스테이징 영역에 추가
- commit: 로컬 저장소에 변경사항 저장
- push: 로컬의 변경사항을 원격 저장소에 반영
- pull: 원격 저장소의 변경사항을 로컬로 가져옴

### 주요 특징
#### 1. 버전 관리
```
SVN: 중앙 서버에 모든 버전이 순차적으로 관리됨
Git: 각 로컬 저장소가 완전한 이력을 가짐
```

#### 2. 네트워크 의존성
```
SVN: 대부분의 작업에 네트워크 연결 필요
Git: 로컬에서 대부분의 작업 가능
```

#### 3. 작업 유연성
```
SVN: 중앙 집중식으로 관리가 용이하지만 유연성이 떨어짐
Git: 분산식으로 더 유연하지만 관리가 복잡할 수 있음
```

### 🫂 브랜치 전략
<img width="579" alt="image" src="https://github.com/user-attachments/assets/e035f7d7-e129-400c-b260-007f217b7332" />


#### 🔥 SVN 브랜치 전략
##### 1. 기본 구조 
```
trunk: 주요 개발 라인
branches: 기능 개발 및 버그 수정용 분기
tags: 릴리스 버전 스냅샷
```

##### 2. 작업 방식
```
대부분의 개발은 trunk에서 직접 진행
큰 기능 개발시에만 branch 생성
브랜치 생성과 병합이 상대적으로 무거움
주로 장기적인 기능 개발에 브랜치 사용
```


##### 3. 실무 적용
```
단순한 브랜치 구조 선호
소규모 팀에 적합
릴리스 주기가 긴 프로젝트에 효과적
```


#### Git 브랜치 전략 (Git-Flow 기준)
##### 1. 기본 구조
```
master: 제품 출시 버전
develop: 개발 통합 브랜치
feature: 기능 개발 브랜치
release: 릴리스 준비 브랜치
hotfix: 긴급 버그 수정 브랜치
```

##### 2. 작업 방식
```
모든 기능 개발은 feature 브랜치에서 진행
브랜치 생성/병합이 가볍고 빠름
병렬 개발이 용이
더 섬세한 버전 관리 가능
```

##### 3. 실무 적용
```
Git-Flow: 큰 규모의 프로젝트
Trunk-Based Development: 빠른 배포가 필요한 경우
GitHub Flow: 단순화된 워크플로우 필요시
```

### SVN vs Git 주요 차이점 비교 정리
#### 1. 저장소 구조
| 항목 | SVN | Git |
|------|-----|-----|
| 구조 타입 | 중앙 집중식 (단일 저장소) | 분산식 (로컬 + 원격 저장소) |
| 오프라인 작업 | 제한적 | 자유로움 |
| 저장소 크기 | 서버 공간만 고려 | 모든 클라이언트가 전체 이력 보유 |

#### 2. 버전 관리 방식
| 항목 | SVN | Git |
|------|-----|-----|
| 버전 식별자 | 리비전 번호 (순차적) | 커밋 해시 (비순차적) |
| 변경 이력 | 중앙 서버에서 관리 | 로컬에서 완벽한 버전 관리 |
| 작업 단위 | 파일 단위 | 변경사항 단위 |

#### 3. 브랜치 관리
| 항목 | SVN | Git |
|------|-----|-----|
| 브랜치 생성 | 디렉토리 복사 (무거움) | 커밋 포인터 (가벼움) |
| 병합 처리 | 서버에서 처리 | 로컬에서 처리 |
| 브랜치 전략 | 단순한 구조 | 다양한 워크플로우 지원 |

#### 4. 협업 및 관리
| 항목 | SVN | Git |
|------|-----|-----|
| 권한 관리 | 파일/디렉토리 단위 세밀한 제어 | 저장소 단위 권한 관리 |
| 학습 곡선 | 단순하고 직관적 | 상대적으로 복잡함 |
| 적합한 프로젝트 | 중소 규모 프로젝트 | 대규모 분산 프로젝트 |

#### 5. 성능 및 특징
| 항목 | SVN | Git |
|------|-----|-----|
| 대규모 저장소 | 속도 저하 발생 | 안정적인 성능 유지 |
| 스토리지 효율성 | 서버 측 효율적 | 모든 클라이언트가 전체 복사본 보유 |
| 네트워크 의존성 | 높음 | 낮음 |

#### 6. 작업 프로세스
| 항목 | SVN | Git |
|------|-----|-----|
| 커밋 과정 | 바로 중앙 서버에 반영 | 로컬 저장소에 커밋 후 push |
| 변경사항 가져오기 | update로 직접 수신 | fetch로 확인 후 merge/pull |
| 충돌 해결 | 서버 측에서 해결 | 로컬에서 해결 후 push |

#### 7. 사용 용이성
| 항목 | SVN | Git |
|------|-----|-----|
| 명령어 | 단순하고 직관적 | 다양하고 복잡한 옵션 |
| UI 도구 | TortoiseSVN 등 | SourceTree, GitKraken 등 |
| 초기 설정 | 간단함 | 상대적으로 복잡함 |

#### 결론
- SVN은 중앙 집중식 관리가 필요하고 단순한 워크플로우를 선호하는 팀에 적합
- Git은 유연한 브랜치 전략과 분산 작업이 필요한 현대적인 개발 환경에 더 적합
- 최근에는 Git이 업계 표준으로 자리잡았으며, 특히 오픈소스 프로젝트에서 널리 사용됨
